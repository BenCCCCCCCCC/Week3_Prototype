# 数据风险分析

## C 视角 - 测试方法限制

### C1 本地双控导致技能与协作行为低估

- 场景描述：本次 baseline 与 post-patch 都由同一名测试者本地双控完成，无法稳定模拟真实多人对抗中的协作、救援沟通、技能博弈和临场反应。
- 污染机制：Survivor 技能、Hunter 技能、团队转点与救援配合的使用频率可能低于真实多人样本。
- 偏差结论：本次数据可以支持“v0.1 对局收束偏快”以及“v0.2 对局时长方向变化”的判断，但不能单独证明技能系统有效或无效。
- 修补方案：在日志中保留 `本地双控` 标注；将技能使用不足写为测试限制；后续多人样本重新验证技能使用频率、逃生率和救援成功率。
- 修补代价：Week 12 只能记录方向性观察，不能把技能与协作结论写成成功判据。

### C2 Survivor 位移技能缺少独立记录

- 场景描述：测试者观察到 Survivor 位移技能在本地双控测试中较少被稳定使用，冲刺后路线修正成本较高。
- 污染机制：本轮 CSV 没有记录技能触发次数、冲刺后碰撞次数、冲刺后被命中率或冲刺后的路线修正时间。
- 偏差结论：如果仅凭主观观察判断位移技能问题，可能把地图路线、双控输入成本或技能参数混在一起。
- 修补方案：下版本增加技能使用次数、冲刺后碰撞次数、冲刺后被命中率等记录项；在新增记录前，不把该问题作为 PATCH-012 成功判据。
- 修补代价：需要额外记录表或新增 telemetry 字段；Week 12 不新增成功指标。

## A 视角 - Patch 验证噪声

### A1 测试者熟练度影响 v0.2 对比

- 场景描述：v0.1 baseline 与 v0.2 post-patch 都由同一名测试者完成。测试者在多轮测试后会更熟悉地图、出生点、密码机位置、椅子位置和开门路线。
- 污染机制：测试者熟练度变化会影响对局时长、首倒时间、修机完成率和逃生率。v0.2 中的指标变化可能部分来自学习效应，而不完全来自 PATCH-012。
- 偏差结论：如果 v0.2 对局时长增加，可能被全部归因到 `repairHoldSeconds`；如果 v0.2 首倒时间延后，可能被全部归因到 `Cover1`。
- 修补方案：v0.2 测试继续使用 `本地双控` 标注；保留同一异常剔除规则；优先比较方向性变化，不把单局结果写成结论。
- 修补代价：无法完全消除学习效应，需要在复盘中声明样本限制。

### A2 三条 PATCH-012 同时进入 v0.2 导致归因混淆

- 场景描述：Week 12 最终将 `repairHoldSeconds`、`rescueHoldSeconds` 和 `Cover1` 位置一起形成 v0.2，再跑 post-patch 测试。
- 污染机制：对局时长、首倒时间、逃生率都可能同时受到多个 Patch 影响。
- 偏差结论：可能把 `+17.6s` 对局时长变化完全写给 PATCH-012-01，或把 `+34.2s` 首倒时间变化完全写给 PATCH-012-03。
- 修补方案：在 `v0.1_vs_v0.2_comparison.md` 与 `patch_note_v0.2.md` 中写明耦合；能单独观察的字段单独写，不能单独归因的指标写为组合结果。
- 修补代价：本轮只能验证 v0.2 组合效果，不能证明每条 Patch 的独立效果。

### A3 首倒时间依赖人工近似记录

- 场景描述：`first_down_time_seconds` 来自测试者现场观察与 Console 可见日志的人工近似记录。
- 污染机制：人工记录可能存在数秒误差；当样本数较小时，均值可能被单局误差影响。
- 偏差结论：首倒时间从 `50.9s` 到 `85.1s` 的方向可以记录，但不能把每一秒差值都解释为精确效果。
- 修补方案：保留 `-1` 不进入首倒均值的规则；后续把首倒时间直接从 telemetry 或结算统计中导出。
- 修补代价：需要额外导出流程或自动化汇总。

### A4 逃生率和救援成功率小样本不可判定

- 场景描述：v0.1 逃生率为 `4 / 16 = 25%`，v0.2 逃生率为 `4 / 20 = 20%`；救援成功率两轮都样本不足。
- 污染机制：少量逃生人数变化即可改变百分比；救援事件不足时，`rescueHoldSeconds` 的作用无法通过救援成功率验证。
- 偏差结论：可能把 `-5pp` 逃生率变化误写为 PATCH 失败，或把个别救援事件误写为 PATCH-012-02 达成目标。
- 修补方案：逃生率只作方向性观察；救援成功率继续标记样本不足；下版本记录救援尝试数、救援成功数与救援中断数。
- 修补代价：需要更多局数，且最好包含多人样本。

### A5 测试前地图可通行性修复影响路线熟悉度

- 场景描述：v0.1 baseline 正式测试前，Map2 做过可通行性修复，包括 2F slab clearance 与部分 `RangeVisual` `SphereCollider` 改为 non-blocking trigger。
- 污染机制：测试者在排查和验证可通行性时会增加对 `Cipher_H3`、`Cipher_M`、`Cipher_H2`、`Chair_R`、`Chair_L`、`Cover1`、右侧楼梯附近路线的熟悉度。
- 偏差结论：v0.1 与 v0.2 中部分路线选择差异可能受熟悉度影响，而不完全来自 PATCH-012-03。
- 修补方案：在实现自检中标记这些处理为 pre-baseline bugfix；不把它们写入 PATCH-012 判定；下版本继续记录追击路线观察。
- 修补代价：无法从 Week 12 小样本中完全剥离路线熟悉度影响。

## B 视角 - 流程误用风险

### B1 为满足有效样本而人为拖延对局

- 反向引导机制：Week 12 要求单局时长少于 90 秒必须标异常，测试者可能为了让局数有效而等待结算。
- 偏差结论：如果只为了超过 90 秒而等待，对局时长会被拉长，但这不代表正常玩法节奏。
- 修补方案：在日志中标注 `本地双控`；保留所有少于 90 秒的异常局；有效局只用于最低 baseline 与 post-patch 计算。
- 修补代价：对局时长指标可以用于判断方向，但不能等同于真实多人对战时长。

### B2 用异常局问题直接决定 Patch

- 反向引导机制：v0.1 中有多局少于 90 秒的异常局，容易诱导测试者直接根据异常局做数值改动。
- 偏差结论：如果直接用异常局判断 Hunter 过强，可能忽略异常局已经被剔除，不应进入核心指标计算。
- 修补方案：五核心指标只统计 `is_abnormal=FALSE` 的有效样本；异常局只作为现象记录；Patch 触发理由必须引用有效样本均值。
- 修补代价：异常局仍可说明 v0.1 存在过快收束现象，但不能单独作为成功判据。

### B3 把 superseded 历史尝试混入正式判定

- 反向引导机制：`Hunter/PlayerController.externalSpeedMultiplier: 1 -> 0.93` 与 `MatchManager.endgameDuration: 15 -> 30` 曾经存在于历史中，容易被写进 v0.2 成果解释。
- 偏差结论：可能把首倒时间延后归因到 Hunter speed，或把逃生率变化归因到 endgameDuration。
- 修补方案：在 Patch Note、自检表和对比表中明确这两个尝试已移出正式组合；不进入 v0.2 post-patch 指标解释。
- 修补代价：文档需要额外说明实现历史，避免读者误读 commit 历史。

### B4 用地图改动隐藏数值副作用

- 反向引导机制：当 PATCH-012-01 与 PATCH-012-03 都影响对局时长和首倒时间时，可能只强调 `Cover1` 路线变化，回避 `repairHoldSeconds` 对整体节奏的影响。
- 偏差结论：地图改动被写成主要原因，导致下版本继续改地图而忽略目标节奏数值。
- 修补方案：耦合表和 Patch Note 必须写明 PATCH-012-01 与 PATCH-012-03 对对局时长、首倒时间存在耦合；接受联合归因。
- 修补代价：本轮无法证明 Cover1 的独立效果，只能保留路线观察项。
